# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev          # API server with hot reload (tsx watch src/index.ts)
npm run worker       # BullMQ workers — separate process, needed for guest import and AI card generation
npm run build        # tsc + copy src/public (email templates) into dist
npx tsc --noEmit     # type-check only
npx prisma migrate dev --name <snake_case_name>   # create + apply a migration
npx prisma generate  # regenerate the client after any schema.prisma change
npm test             # unit tests: src/**/*.test.ts, no database, Redis or .env needed (runs in CI)
npm run test:e2e     # end-to-end tests: tests/*.test.ts against the running API and its database
```

Both test scripts use `node:test` through tsx. `npm test` covers pure helpers (reminder timing, the RSVP update, phone numbers): put a `<name>.test.ts` beside the file it tests, and keep it free of DB, Redis and env imports. `npm run test:e2e` calls the running API (`npm run dev`) and its database, creating and deleting its own throwaway users. The `src/utils/*.check.ts` scripts are run by hand with `npx tsx`: `inviteCardGeneration.check.ts` (AI invite card error classification, image normalisation, design fingerprint; no DB, also run in CI), and the DB-backed `auth`, `credits`, `updatedAt` and `inviteCardSweep` checks. Both the API and the worker need PostgreSQL (`DATABASE_URL`) and Redis (`REDIS_HOST`/`REDIS_PORT`, also used by the rate limiters). API docs are served at `/reference` (Scalar) from `src/openapi.json`, which is generated by `npm run docs:openapi` (`scripts/generate-openapi.ts`) from a route table plus each route's zod schema — when adding or changing a route, update that table and regenerate. Health check: `GET /health` (503, naming the dependency, when PostgreSQL or Redis does not answer within 2 s).

The frontend is the sibling repo `../ai-wedding-rsvp-generator-frontend`.

## Architecture

**Request flow** — `routes → controller → service → repository`, one file per resource in each folder. Routers are mounted in `src/index.ts` under `/api/<resource>`; note `eventInviteFormat.*` is mounted at `/api/page-setting` (the `GuestEventInviteFormat` model holds each event's RSVP page settings: which questions to ask, reminder toggles, illustration).
- Routes chain `authenticate, validate(schema), asyncHandler(controller)`. `validate` (`middlewares/validate.middleware.ts`) parses `{ body, query, params }` with a zod object from `src/validations` and writes the parsed values back onto `req`, so defaults/transforms apply. Zod `.infer` types from the same file type the controller's `Request<Params, {}, Body, Query>`.
- Controllers respond with `sendSuccess(res, message, data, status)` (`utils/response.util.ts` → `{ success, statusCode, message, data }`). Throw `new ApiError(status, message)` anywhere; `middlewares/error.middleware.ts` turns it into the response, anything else becomes a 500.
- Repositories are plain functions over `prisma` taking an optional `tx?: Prisma.TransactionClient`; services run multi-step writes in `prisma.$transaction(async (tx) => …)` and pass `tx` down.
- **Ownership is not enforced by middleware.** Every service/controller must check that the wedding/event/guest belongs to `req.user.id` (e.g. `getUserWeddingService`, `verifyWeddingEventOwnershipService`, or a `where: { …, wedding: { user_id } }` query).

**Prisma** — Prisma 7 with the `pg` driver adapter (`src/lib/prisma.ts`). The client is generated to `generated/prisma`, so import types/enums from `../../generated/prisma/client` (or `/enums`), not `@prisma/client`. Migration folders are `YYYYMMDDHHMMSS_snake_case_name`; recent ones start `migration.sql` with a short comment explaining why. Every model's `updated_at` is `@updatedAt`, so never set it by hand; any update, including `updateMany`, moves it (`npx tsx src/utils/updatedAt.check.ts`).

**Auth** — `authenticate` expects `Authorization: Bearer <access token>`; tokens (access/refresh/verify-email/reset-password, `enums/token.enum.ts`) are JWTs also stored in the DB and checked by `verifyTokenService`. Sessions are per device: the access and refresh token of one sign-in share `Token.session_id`, a refresh rotates only that session's pair (deleting the used refresh token is the gate against reuse), logout ends only that session, and a password reset deletes all of the user's tokens. `req.user` is typed in `src/types/express.d.ts`. The public RSVP routes (`/api/rsvp/:token`) use the per-event `GuestEventInvite.invite_token` as the only credential. Hosts can set a guest's reply (the Guest Details status dropdown) through the authenticated `PUT /api/rsvp/invite/:inviteId` (ownership-checked, not bound by the RSVP deadline); both paths share `rsvp.service.ts` `saveReply`, including the live dashboard event.

**Background jobs** (BullMQ, `src/queues` + `src/workers`) — the API enqueues and returns `202 { jobId }`; the worker process runs the job via a service function and its return value is the job result; the client polls a status endpoint.
- `guest-import-queue` (`guest.queue.ts`) runs `parse-excel` guest imports; its payload is a union discriminated on `type` so more job kinds can share the queue. Status: `GET /api/guest/import-status/:jobId`, which checks `job.data.userId` against the caller — keep `userId` in job payloads.
- `inviteCard.queue.ts` (`ai-invite-card-queue`) runs `runInviteCardGenerationJob` (`inviteCard.service.ts`); status lives on the `EventInviteCard` row. The same file schedules the stale-generation sweep on `ai-invite-card-sweep-queue`.
- New workers must be added to the array in `src/workers/index.ts`. Use `attempts: 1` for jobs that aren't safe to repeat (e.g. sending messages).

**Live RSVP updates** — `GET /api/wedding/:id/live` is a server-sent events stream. `emitRsvp` (`lib/rsvpEvents.ts`, called after an RSVP is saved in `rsvp.service.ts`) publishes to the Redis channel `live-rsvp`; each process that streams dashboards opens one lazy subscriber connection and fans messages out to its local SSE listeners via `onRsvp`. So emits work from any API instance or the worker, and publish failures are logged, never thrown. Check-ins travel the same way: `POST /api/guest/invites/check-in` (the host scans the invite token from the guest's QR; owner-only, idempotent) sets `GuestEventInvite.checked_in_at` and emits a `check-in` SSE event; per-event stats carry `arrivedGuests`.

**External services**
- Images: clients upload/view directly via S3 presigned URLs (`/api/general/generate-upload-url`, `generate-view-url`; `services/aws.service.ts`). The DB stores S3 object keys, not URLs. `general.service.ts` rewrites every upload key under `users/<userId>/` (clients must save the returned `object_key`), and only issues view URLs for keys under the caller's prefix or saved on a record they own (`isObjectKeyReferencedByUser` in `repositories/general.repository.ts` — add new key columns there); anything else is a 404.
- AI invite cards: `runInviteCardPipeline` (`services/inviteCardGeneration.service.ts`, model `gemini-3-pro-image`, 9:16) runs DESIGN (text-less artwork, saved to `invite_design_image_url` with `design_fingerprint`, a hash of the built stage 1 prompt plus its image keys) then TYPESETTING; an attempt skips DESIGN when the stored fingerprint still matches, so job retries, "Try again" and text-only edits reuse the artwork instead of redrawing. Prompts are assembled in `utils/*PromptBuilder*`/`*Catelogue*` utils. Every Gemini call, including the RSVP page header image (`utils/geminiImageEditor.util.ts`, synchronous, `toHeaderImageError` turns failures into 422/502/503/504 responses after the refund), goes through `generateImage` (`utils/geminiImage.util.ts`: 120s abort per call, in-call retry for `OVERLOADED` only, failures classified into `GENERATION_ERROR_CODE` and stored as `generation_error_code` for the UI to explain). The queue allows 3 attempts with 30s/90s backoff for retryable codes; the job throws `UnrecoverableError` for the rest (billing, safety, invalid input), and a card is COMPLETED only once typesetting has saved a final image. Source images are normalised with sharp (`utils/imageNormalize.util.ts`: EXIF rotate, longest side 2048px, JPEG/PNG with a truthful mime type). The worker writes `generation_heartbeat_at` at every stage and retry, and a card silent for 10 minutes is failed with `TIMEOUT` and refunded, by the worker's sweep (a repeating job on `ai-invite-card-sweep-queue`, every 2 minutes) or by the status endpoint, whichever sees it first (`retireStaleGeneration` in `inviteCard.service.ts`; check with `npx tsx src/utils/inviteCardSweep.check.ts`). A generation job that starts after its run was retired exits without generating. Each new final image (generated, or an uploaded card saved through `PATCH /invite-card/:id`) is also written to `EventInviteCardVersion` (newest 10 per card); `GET /invite-card/:id/versions` lists them and `POST .../versions/:versionId/restore` puts one back as `generated_invite_image_url`.
- AI credits: `User.ai_credits`, spent per generation (`AI_CREDIT_COST` in `services/credits.service.ts`: invite card, RSVP header image) by `spendCredits`, whose balance check sits in the `WHERE` so it can't go below zero (402 when short); failed generations are refunded with `refundCredits`. Every change also writes a `CreditTransaction` row in the same transaction (reason, delta, the card or event id), so 100 + a user's rows = `ai_credits`; admins top up with `npx tsx scripts/grant-credits.ts <email> <amount> "<note>"`. `GET /api/auth/me` returns the costs as `ai_credit_costs` for the frontend. Check with `npx tsx src/utils/credits.check.ts`.
- Email: AWS SES or SMTP via Nodemailer (switch with `EMAIL_PROVIDER=ses|smtp`) with Handlebars templates in `src/public/emailTemplates` (`services/email.service.ts`).
- WhatsApp: no API integration. `GET /api/guest/invites/whatsapp?eventId=|guestId=` returns `wa.me` click-to-chat links with the invite message pre-filled (message built in `guest.service.ts` `formatInviteMessage`; guest mobile numbers are stored as typed and normalized by `normalizePhone` in `lib/whatsapp.ts`, using `WHATSAPP_DEFAULT_COUNTRY_CODE`). The couple sends each message from their own WhatsApp, and the frontend calls `POST /api/guest/invites/:inviteId/mark-sent` on click, which sets `GuestEventInvite.invite_sent_at`. Reminders work the same way: `GET /api/guest/invites/reminders?eventId=` lists reminders due now (rules in `utils/reminder.util.ts`: first reminder 7 days after the invite was sent, final reminder within 3 days of `invite_deadline`, both gated by the event's `first_reminder`/`final_reminder` toggles), marked via `POST /api/guest/invites/:inviteId/mark-reminded`. `DELETE` on either `mark-sent` or `mark-reminded` (the latter with `?reminder=FIRST|FINAL`) undoes the mark, for a mis-tap. The RSVP deadline is set per event on `GuestEventInviteFormat.rsvp_deadline` and copied onto every invite's `invite_deadline` when saved and when invites are created — `invite_deadline` is what the RSVP link enforces. Deadlines in messages and the dashboard's 7 day buckets use the wedding's IANA `Wedding.timezone` (default `Asia/Kolkata`; helpers in `utils/timezone.util.ts`); event dates are calendar dates and always format in UTC.

**Config** — `src/config/env.ts` validates env vars with zod once at startup (imported first by `src/index.ts` and `src/workers/index.ts`; exits listing every problem). Read config as `env.X` from that module (typed, numbers coerced, defaults applied), never `process.env.X`; the one exception is `lib/whatsapp.ts`, kept import-free for its unit test. Importing anything that reaches `env` (the logger, prisma, redis, most services) needs a valid env. Add any new variable to both `env.ts` and `.env.example`. Guest mobile numbers are validated with the same `normalizePhone` rule the WhatsApp links use. `WEB_APP_URL` is both the CORS origin (so it has no trailing slash, e.g. `http://localhost:5173`) and the base for links sent to users — join paths with an explicit `/` (as `createUrl` in `utils/utils.ts` and `buildRsvpUrl` in `guest.service.ts` do). Rate limiters (`middlewares/rateLimiter.middleware.ts`): `globalLimiter` on all `/api`, plus `authLimiter`, `rsvpLimiter`, `imageGenerationLimiter` on specific routes. TypeScript runs with `strict: false` but `strictNullChecks` on (guard nullables, no bare `!`; `req.user` is typed as always set because only `authenticate`d routes read it), CommonJS output.

**Logging** — pino (`src/config/logger.ts`) at `LOG_LEVEL` (default `info`): coloured lines when `NODE_ENV` is `local`/`development`, JSON lines on stdout otherwise; a file only when `LOG_FILE` is set. Request and error logs pass URLs through `redactUrlForLog` (`utils/logUrl.util.ts`), which hides the public RSVP token.

**Deployment** — a single Docker image (`dockerfile`) builds the app and `start.sh` runs Redis, the worker, and the API together in one container.

## Conventions and quirks

- Deliberate shortcuts are marked with `// ponytail:` comments naming the limitation and the upgrade path.
- Existing misspellings are part of the API/schema — keep them when referencing: `verfiyWeddingOwnershipService`, `accomodation_*` guest fields, `Dietary.NON_VEGETARAIN`, `*Catelogue` util names, and `eventInviteFormat.route.ts` (singular, unlike the other route files).
